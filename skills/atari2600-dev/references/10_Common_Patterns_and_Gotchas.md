# Common Patterns and Gotchas

This document catalogues the most frequent bugs, the kernel stability checklist, cycle-counting pitfalls, and debugging strategies for Atari 2600 development.

## 1. Kernel Stability Checklist

Every frame must produce exactly 262 scanlines (NTSC) or 312 scanlines (PAL). If your picture rolls, shakes, or the Stella `_scanEnd` value is wrong, check each section:

| Section | NTSC Lines | PAL Lines | Method |
|---------|-----------|-----------|--------|
| VSYNC | 3 | 3 | `VERTICAL_SYNC` macro |
| VBLANK | 37 | 45 | `TIMER_SETUP VBLANK_LINES` |
| Visible kernel | 192 | 228 | WSYNC loop or timer |
| Overscan | 30 | 36 | `TIMER_SETUP OVERSCAN_LINES` |
| **Total** | **262** | **312** | Verify with `_scanEnd` |

### Validating with Stella

The headless Stella debugger reports the frame's scanline count via the `_scanEnd` pseudo-register:

```
frame #60
print _scanEnd
```

Expected output: `_scanEnd = 262` (NTSC) or `_scanEnd = 312` (PAL).

You can also set a breakpoint to catch bad frames:
```
breakIf { _scanEnd != 262 }
```

## 2. The #1 Bug: Game Logic in the Kernel

**The single most common and destructive mistake** is placing game logic (input reading, collision processing, branching decisions) inside the visible kernel. The kernel has exactly 76 CPU cycles per scanline. Variable-length code paths (branches taken vs not taken, conditional blocks) cause the scanline count to vary frame-to-frame.

### Bad Example

```asm
; DON'T DO THIS — branching in the kernel
.kernelLoop:
    sta WSYNC
    lda SWCHA            ; read joystick (variable timing!)
    and #%00010000
    beq .moveUp          ; branch = 3 cycles; no branch = 2 cycles
    ; ... game logic here ...
.moveUp:
    inc PlayerY          ; modifying state in the kernel!
    lda SpriteData,y
    sta GRP0
    dey
    bne .kernelLoop
```

This kernel's cycle count changes depending on joystick state, causing visible jitter and incorrect `_scanEnd`.

### Good Example

```asm
; DO THIS — pre-calculate everything in VBLANK
; VBLANK:
    lda SWCHA
    and #%00010000
    beq .moveUp
    jmp .doneInput
.moveUp:
    inc PlayerY
.doneInput:
    ; Pre-calculate all kernel data here

; KERNEL — only drawing, no logic:
.kernelLoop:
    sta WSYNC
    lda SpriteData,y    ; pre-calculated data only
    sta GRP0
    dey
    bne .kernelLoop
```

**Rule**: The kernel draws. VBLANK and overscan think.

## 3. Cycle Counting Errors

### Branch Timing

| Condition | Cycles |
|-----------|--------|
| Branch not taken | 2 |
| Branch taken (same page) | 3 |
| Branch taken (page cross) | 4 |

A branch that crosses a `$100` page boundary costs an extra cycle. This is a frequent source of off-by-one scanline bugs.

### Page Crossing in Indexed Addressing

`LDA table,X` takes 4 cycles normally but **5 cycles** if `table + X` crosses a page boundary. In tight kernel code, this extra cycle can break timing.

**Fix**: Align data tables on page boundaries:
```asm
    align 256
SpriteData:
    .byte %00111100, %01111110, ...
```

### WSYNC Placement

`sta WSYNC` halts the CPU until the end of the current scanline (cycle 76). Place it at the **top** of your kernel loop, not the bottom:

```asm
; Correct — WSYNC at top
.kernelLoop:
    sta WSYNC         ; sync to start of scanline
    ; ... 73 cycles of drawing ...
    dey
    bne .kernelLoop

; Wrong — WSYNC at bottom risks drift
.kernelLoop:
    ; ... drawing ...
    dey
    sta WSYNC         ; if drawing took > 76 cycles, this syncs to NEXT line
    bne .kernelLoop   ; skipped a scanline!
```

### Checking Cycle Counts

The `.lst` listing file generated by dasm shows the assembled bytes and addresses for each instruction. Use the 6502 cycle count table to manually verify kernel timing. Each scanline budget:

```
76 total cycles
-3 sta WSYNC
-2 dey / dex
-3 bne (taken)
= 68 cycles available for drawing
```

## 4. HMOVE Bar

### Root Cause

`HMOVE` extends horizontal blank by 8 colour clocks, producing a visible black bar (8 pixels wide) at the left edge. Additionally, it sends extra clock pulses to position counters.

### Avoidance Rules

1. **Execute `sta HMOVE` immediately after `sta WSYNC`** (within the first 3 cycles of the scanline). This places the extension entirely within the normal HBLANK period.
2. **Do not write to HMxx registers within 24 cycles after HMOVE.** The position counters are still being adjusted.
3. **Perform all motion during VBLANK or overscan** when possible — HMOVE bars are invisible when the beam is blanked.
4. **Hiding technique**: If you must HMOVE during the visible kernel, set `COLUBK` to black at the left edge and restore it after the HMOVE bar region.

## 5. Common Beginner Bugs

### Uninitialised RAM

RAM contents are random at power-on. Always start with `CLEAN_START`:
```asm
InitSystem:
    CLEAN_START       ; zeros all RAM, resets stack, clears decimal mode
```

### Forgetting CXCLR

Collision latches persist until cleared. If you forget `sta CXCLR` after reading collisions, old flags remain set and cause false positives every subsequent frame.

### Not Disabling Unused Objects

Players, missiles, and the ball remain visible until explicitly disabled. Always zero out graphics for unused objects:
```asm
    lda #0
    sta GRP0
    sta GRP1
    sta ENAM0
    sta ENAM1
    sta ENABL
```

### Wrong Include Paths

dasm requires correct relative paths. If your project uses the standard structure (`src/`, `include/`, `build/`), includes should be:
```asm
    include "../include/vcs.h"
    include "../include/macro.h"
    include "../include/tv_modes.h"
```

### Missing `processor 6502`

The first directive in every `.asm` file must be `processor 6502`. Without it, dasm uses the wrong instruction set.

### Exceeding 4 KB Without Bank Switching

If your assembled ROM exceeds 4096 bytes, dasm will produce a file larger than 4 KB. Stella may not load it correctly without bank-switching support. See [09_Advanced_Techniques.md] for bank switching.

### Reading SWCHA with Wrong Bit Mask

P0 joystick bits are in the high nibble (D7-D4), P1 in the low nibble (D3-D0). A common mistake is testing the wrong bits. See [06_Input_and_Collision.md] for the correct layout.

### SetHorizPos Without Prior HMCLR

The SetHorizPos routine writes to HMPx. If old motion values remain in other HMxx registers, calling `sta HMOVE` will apply those stale values too. Always `sta HMCLR` before the first SetHorizPos call in a sequence.

## 6. Performance Optimisation

### Zero-Page Access

Addresses `$00`-`$FF` (zero page) save 1 byte and 1 cycle per access compared to absolute addressing. Store all frequently-used variables in zero page (`$80`-`$FF` = RAM).

### Lookup Tables vs Runtime Calculation

Pre-computed tables trade ROM space for CPU cycles. A 256-byte sine table costs 256 bytes of ROM but saves dozens of cycles per lookup compared to computing sine at runtime.

### Loop Unrolling

In the kernel, branch overhead (2-3 cycles) per iteration adds up. For short loops (5-10 iterations), unrolling eliminates this:

```asm
; Unrolled: 6 identical scanlines (no loop overhead)
    sta WSYNC
    stx COLUBK
    sta WSYNC
    stx COLUBK
    sta WSYNC
    stx COLUBK
    ; ... etc
```

### RIOT Timer vs WSYNC Counting

For VBLANK and overscan, use `TIMER_SETUP`/`TIMER_WAIT` instead of counting WSYNC loops. The timer runs in the background, freeing the CPU for game logic.

## 7. Debugging Workflow

### Step 1: Check Assembly

Run dasm and verify it completes without errors. Check the `.lst` file for unexpected addresses or byte counts.

### Step 2: Check Scanline Count

Run the ROM in headless Stella with a `.script` file:
```
frame #60
print _scanEnd
exitRom
```

If `_scanEnd` != 262, your frame structure is wrong. Common causes:
- Game logic in the kernel (variable cycle counts)
- Wrong TIMER_SETUP value
- Extra or missing `sta WSYNC` calls

### Step 3: Visual Debugging with COLUBK

Set `COLUBK` to different colours in each frame section to visually confirm timing:

```asm
    ; VBLANK
    lda #$1A           ; yellow
    sta COLUBK
    ; ... VBLANK code ...

    ; Kernel
    lda #$00           ; black (normal)
    sta COLUBK
    ; ... kernel ...

    ; Overscan
    lda #$4A           ; red
    sta COLUBK
```

If yellow or red bleeds into the visible area, that section is taking too many scanlines.

### Step 4: Inspect Variables

Use the Stella `ram` command in your `.script` file to dump all 128 bytes of RAM. Check that variables have expected values at the frame you're testing. See [03_Toolchain_and_Stella_Debugger.md] for the full Stella debugger command reference.

### Step 5: Check the .sym File

The `.sym` symbol file shows resolved addresses for all labels. Verify that:
- ROM code starts at `$F000` (4K) or `$F800` (2K)
- Variables are in `$80`-`$FF` range
- Interrupt vectors are at `$FFFC`-`$FFFF`
